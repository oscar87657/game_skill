# 01. 이동 시스템 — 직접 제어와 물리 안정성은 어떻게 함께 얻는가?

> 결론 요약: 현재 규모에서는 `CharacterController`가 충돌을 처리하고
> `SideScrollerMotor`가 속도와 상태를 직접 소유하는 방식이 정밀한 2.5D 조작에
> 적합하다. 물리 오브젝트와의 상호작용이 핵심이면 Rigidbody가, 복잡한 지형
> 규칙과 이동 상태가 더 늘어나면 Custom Kinematic Motor와 상태 모듈 분리가
> 더 적합하다.

## 1. 장르에서의 역할

메트로배니아에서 이동은 단순한 위치 변경이 아니라 월드를 읽는 언어다. 기본
점프의 높이, 대시 거리와 공중 자원의 수가 곧 레벨의 도달 가능 범위를 만들고,
새 능력을 얻은 뒤 같은 공간을 다르게 해석하게 한다.

- 플레이어 경험: 입력 직후 의도가 전달되고 실수는 짧게 보정되지만, 공중 행동의
  사용 횟수와 도달 거리는 예측 가능해야 한다.
- 탐험 연결: 2단 점프·공중 대시·벽 이동이 과거의 높은 발판과 긴 틈을 새 경로로
  바꾼다.
- 전투 연결: 대시는 이동과 무적, 공중 공격은 짧은 수직 보정만 요청하며 수평
  제어권은 이동 시스템이 유지한다.
- 레벨 제약: 점프 정점, 대시 거리, 벽 반발 거리, 경사·단차 허용치가 Graybox의
  최소·최대 간격 기준이 된다.

이 시스템이 불안정하면 레벨이 실제 능력보다 입력 우연에 좌우되고, 능력 게이트와
백트래킹 경로도 일관된 규칙으로 설계할 수 없다.

## 2. 연구 질문과 성공 조건

### 연구 질문

정밀한 횡스크롤 입력, 경사·단차 충돌, 능력별 공중 자원과 전투 연계를 하나의
이동 계약으로 유지하려면 CharacterController, Rigidbody, Custom Kinematic
Motor 중 현재 규모에서 무엇을 선택해야 하는가?

### 성공 조건

| 관점 | 성공 조건 |
|---|---|
| 플레이 결과 | 이동·점프·대시가 즉시 반응하고 경사와 0.3m 단차를 점프 없이 통과한다. |
| 입력 보정 | 코요테 타임과 점프 버퍼가 각각 `0.12초` 범위의 빠르거나 늦은 입력을 허용한다. |
| 능력 진행 | 해금 전에는 공중 행동을 거부하고, 해금 뒤 2단 점프·공중 대시·벽 이동을 같은 Motor가 제공한다. |
| 전투 계약 | 공격은 짧은 체공만 요청하고 수평 속도, 대시 취소와 착지는 Motor가 계속 소유한다. |
| 경계 상황 | 대시 이동·무적·쿨다운, 벽 점프·입력 잠금, 착지·공중 자원 리필이 서로 다른 상태로 남는다. |
| 검증 | 핵심 수식은 EditMode, Scene 연결은 PlayMode, 손맛과 동선은 실제 플레이로 확인한다. |

## 3. 현재 구현 분석

| 코드 | 책임 | 장르 경험으로 이어지는 결과 |
|---|---|---|
| `SideScrollerMotor.cs` | 입력 액션, 짧은 타이머, 수평·수직 속도와 `CharacterController.Move` 실행 | 걷기·달리기·점프·대시·벽 이동이 하나의 속도 소유권을 사용 |
| `MovementMath.cs` | 입력 정규화, 방향, 대시 곡선, 포물선 점프 속도 계산 | 키보드·스틱의 공통 계약과 예측 가능한 점프·대시 |
| `WallTraversalMath.cs` | 벽 법선, 벽 방향 입력, 미끄러짐과 반발 속도 계산 | 좁은 샤프트에서도 일관된 벽 잡기·벽 점프 |
| `PlayerAbilityState.cs` | 획득한 이동 능력 ID 보유 | 같은 이동 코드가 해금 전후의 도달 범위를 변경 |
| `PlayerCombat.cs` | 공중 공격 때 제한된 체공 시간을 요청 | 공격이 이동 상태 전체를 빼앗지 않고 연계 가능 |
| `PlayerAnimator.cs` | 확정된 속도·상태를 Animator 표현으로 변환 | 로직 상태와 Humanoid 표현 분리 |

### 실행 흐름

```text
Input System
  → SideScrollerMotor가 입력 의도와 타이머 갱신
  → 능력 ID·접지·최근 벽 접촉으로 행동 가능 여부 판단
  → MovementMath / WallTraversalMath가 방향과 속도 계산
  → CharacterController.Move로 X/Y 이동
  → Z 깊이 고정
  → 확정 상태를 Animator·Feedback·Tutorial 이벤트에 전달
```

`SideScrollerMotor`는 상태의 오케스트레이터다. `MovementMath`와
`WallTraversalMath`는 `Time`, Transform과 Collider를 읽지 않으므로 같은
입력에 같은 결과를 낸다. 반면 접지, 벽 접촉과 실제 이동은 Unity 물리 결과이므로
Controller에 남긴다.

![이동 시스템 코드 구조](../../Media/Diagrams/01-movement-architecture.png)

### 상태 소유권

| 상태 | 소유자 | 분리 이유 |
|---|---|---|
| 수평·수직 속도 | `SideScrollerMotor` | 공격과 애니메이션이 서로 다른 속도를 덮어쓰지 않게 함 |
| 코요테·입력 버퍼 | `SideScrollerMotor` | 프레임 입력과 접지 전환의 시간 순서를 한곳에서 해결 |
| 대시 이동·무적·쿨다운 | 각각의 Motor 타이머 | 이동 종료와 피격 허용, 다음 사용 시점을 독립 조정 |
| 공중 점프 횟수·공중 대시 충전 | `SideScrollerMotor` | 착지와 승인된 점프에서만 결정적으로 리필 |
| 능력 보유 | `PlayerAbilityState` | Pickup·Save와 이동 실행을 분리 |
| 공중 공격 체공 요청 | `PlayerCombat` → Motor | 전투는 의도만 전달하고 실제 속도는 Motor가 적용 |

## 4. 구현 후보 비교

### 이동 충돌 방식

| 후보 | 플레이 감각 | 레벨·물리 | 테스트·결합 | 확장 비용 | 적합한 상황 |
|---|---|---|---|---|---|
| CharacterController + 명시적 속도 (현재) | 가속·정지·공중 제어를 직접 결정 | 경사·Step Offset 제공, 힘 반응은 직접 구현 | 규칙 분리 시 테스트 가능, Unity 접지는 통합 검증 필요 | 상태가 늘면 Motor가 커짐 | 정밀 조작이 핵심인 소규모 2.5D 액션 |
| Rigidbody + Force/Velocity | 충격·밀기·Moving Body 상호작용이 자연스러움 | 물리 재질·FixedUpdate·보간 조정 필요 | 물리 환경에 결과가 더 의존 | 복잡한 힘 상호작용에는 유리 | 넉백·물리 퍼즐·동적 오브젝트가 핵심인 게임 |
| Custom Kinematic Motor | 지형 질의와 슬라이드 규칙을 완전히 통제 | One-way·이동 발판·특수 경사를 세밀하게 구현 | 계산 계층을 가장 넓게 테스트 가능 | 충돌 해결과 유지 비용이 큼 | 이동 규칙이 콘텐츠의 중심이고 지형 종류가 많은 프로젝트 |
| Transform 직접 이동 | 반응이 단순하고 제작이 빠름 | 충돌·경사·관통을 모두 직접 처리 | 초기 코드는 작지만 기능마다 예외 증가 | 프로토타입 이후 급격히 증가 | 충돌 없는 감각 실험 또는 매우 초기 Graybox |

### 이동 상태 구성 방식

| 후보 | 장점 | 단점 | 선택 조건 |
|---|---|---|---|
| 하나의 Motor + 순수 계산 분리 (현재) | 속도 소유권과 프레임 순서가 한눈에 보이고 작은 규모에서 디버깅이 빠름 | 점프·대시·벽·공격 보정이 늘수록 `Update` 분기 증가 | 행동 수가 제한되고 한 사람이 빠르게 반복하는 현재 프로토타입 |
| 행동별 State 객체 | Enter/Update/Exit와 우선순위를 명시 가능 | 공중 점프·공격처럼 동시에 허용할 행동을 단일 상태로 표현하기 어려움 | 상호 배타적인 경직·수영·사다리·컷신 상태가 크게 늘 때 |
| 능력별 Component 조합 | 기능 단위 교체와 캐릭터 변형에 유리 | 여러 Component가 속도와 취소 권한을 경쟁할 수 있음 | 플레이어 종류와 장착 능력 조합이 많고 중재 계약이 준비됐을 때 |

### 입력 보정 방식

현재는 코요테 타이머와 점프 버퍼를 별도로 둔다. 즉시 접지 여부만 검사하는
방식보다 관대하지만, 두 타이머가 동시에 유효할 때 지상 점프를 우선한다. 입력
Command Queue는 공격·이동을 공통 순서로 기록할 수 있으나, 현재 행동 수에서는
추적 비용과 디버깅 복잡도가 더 크다.

## 5. 선택과 전환 기준

### 현재 프로젝트에서의 선택

- 선택: CharacterController + 하나의 Motor 오케스트레이터 + 순수 계산 함수
- 우선 기준: 짧은 입력 반응, 일정한 도달 거리, 경사·단차 안정성, 빠른 수치 반복
- 감수한 단점: 물리 힘과 이동 발판 대응을 직접 구현해야 하고 Motor의 상태 수가
  늘어난다.
- 보완: 계산을 `*Math`로 분리하고 이동·무적·쿨다운 타이머를 합치지 않으며,
  전투에는 속도 변경 대신 제한된 요청 API만 공개한다.

### 다른 방식이 더 나은 경우

- 단순 충돌 없는 프로토타입: Transform 직접 이동이 더 빠르다.
- 넉백·밀기·물리 퍼즐이 핵심: Rigidbody가 상호작용 비용을 줄인다.
- 이동 발판, One-way, 사다리, 물·중력 전환과 특수 경사가 핵심 콘텐츠가 됨:
  Custom Kinematic Motor를 검토한다.
- 다수 캐릭터가 서로 다른 능력 조합을 사용함: 능력별 Component와 중앙
  Movement Arbiter가 더 적합하다.

현재 구조를 분리해야 하는 구체적인 신호는 다음과 같다.

1. 새 행동 하나를 추가할 때 `Update`, 점프 판정, Reset과 전투 취소를 모두
   수정해야 한다.
2. 서로 동시에 가능한 상태와 배타적인 상태의 우선순위 버그가 반복된다.
3. 이동 발판과 외부 힘 때문에 Motor 밖의 코드가 속도를 직접 쓰기 시작한다.
4. 플레이어 변형마다 같은 Motor의 조건문이 늘어난다.

## 6. 핵심 판단 읽기

### 대시 곡선

```csharp
float curveMultiplier = MovementMath.DashSpeedMultiplier(
    dashProgress,
    dashEdgeSpeedMultiplier);
horizontalSpeed = dashDirection * dashSpeed * curveMultiplier;
```

```text
t = clamp(dashElapsed / dashDuration, 0, 1)
multiplier = edge + (1 - edge) × sin(π × t)
```

`edge = 0.72`이므로 시작과 끝은 최고 속도의 72%, 중앙은 100%다. 양 끝을
0으로 만드는 Ease In/Out은 짧은 회피에서 느린 출발과 급제동처럼 느껴졌고,
상수 속도는 기계적으로 보였다. 사인 곡선은 총 시간이 짧아도 최고점 전후의
변화를 보여주며 출발 반응은 유지한다.

계산을 `Update()`에서 `MovementMath`로 옮겨 양 끝과 중앙의 계약을 Scene 없이
검증하고, 끝 속도 배율은 Inspector에서 조정할 수 있게 했다.

### 점프 우선순위

```text
최근 접지이면 지상 점프
  아니고 최근 벽 접촉 + 벽 능력이면 벽 점프
  아니고 남은 횟수 + 2단 점프 능력이면 공중 점프
```

실제 코드는 유효 조건을 먼저 계산한 뒤 승인된 점프만 공중 대시를 충전한다.
버튼 입력만으로 자원을 충전하지 않기 때문에 대시 중 거부된 점프나 능력 미해금
입력이 상태를 바꾸지 않는다.

### 이동과 회피 판정 분리

대시 이동은 `0.2초`, 무적은 `0.3초`, 쿨다운은 `0.48초`다. 이동 타이머를 무적
상태로 재사용하지 않아 종료 경계의 작은 입력 오차는 보호하면서 쿨다운 전체가
무적이 되는 문제는 막는다.

자동 테스트가 아직 직접 보장하지 않는 항목도 있다. 코요테 타임과 점프 버퍼의
프레임 경계, 실제 이동 궤적, 공중 대시 리필, 이동 발판은 현재 수동 플레이와
Scene 조립 테스트에 의존한다. 이는 다음 이동 실험의 우선 테스트 대상이다.

## 8. 시연 자료

### 기본 이동과 공중 자원

![기본 이동 흐름](../../Media/GIF/01-01-movement-flow.gif)

가속 이동과 지상 대시 뒤 `점프 → 2단 점프 → 공중 대시 → 착지`가 이어진다.
착지는 공중 점프와 대시 자원을 초기화하고, 승인된 점프는 공중 대시만 다시
충전하는 현재 자원 계약을 보여준다.

### 대시 곡선과 달리기 전환

![대시 속도 곡선과 달리기 전환](../../Media/GIF/01-02-dash-curve.gif)

앞부분은 정상 속도, 뒷부분은 같은 입력의 `0.45배속`이다. 출발·종료 속도를
남긴 사인 곡선과, Shift를 계속 누르면 대시 종료 뒤 Sprint 상태로 전환되는
두 규칙을 확인할 수 있다.

### 대시 이동과 무적의 별도 수명

![일반 피격과 대시 무적 비교](../../Media/GIF/01-03-dash-invulnerability.gif)

일반 상태에서는 탄환 피격이 확정되고, 대시에서는 데미지만 거부한 채 탄환은
계속 이동한다. 이동 타이머와 무적 타이머를 분리했기 때문에 가능한 결과다.

### 벽 이동

![벽 잡기와 연속 벽 점프](../../Media/GIF/01-04-wall-traversal.gif)

벽 방향 입력과 최근 접촉이 함께 유효할 때만 짧게 잡고 이후 낙하 속도를
제한한다. 반발 속도 `3.6`과 입력 잠금 `0.04초`는 좁은 샤프트에서 반대편 벽을
놓치지 않도록 조정한 값이다.

### 경사와 작은 단차

![경사면과 작은 단차](../../Media/Screenshots/01-05-slope-step.png)

Main의 15도 경사 끝에 있는 작은 수직 단차를 점프 없이 통과한다.
CharacterController의 `Slope Limit 45°`와 `Step Offset 0.3m`가 직접 제어
속도와 함께 동작하는 통합 결과다.

## 9. 결론

- 메트로배니아의 이동 값은 캐릭터 감각뿐 아니라 레벨의 거리·높이 문법이다.
- 현재 규모에서는 속도의 단일 소유자가 자유로운 공격·대시 연계를 안정시키며,
  계산 분리는 CharacterController 선택의 테스트 약점을 보완한다.
- 타이머는 이름이 비슷해도 수명이 다른 계약이다. 대시 이동·무적·쿨다운과
  점프 버퍼·코요테 시간을 합치지 않아야 각각 독립 조정할 수 있다.
- 능력 해금은 별도 상태가 소유하고 Motor는 사용 가능 여부만 읽어, Pickup과
  저장 방식이 바뀌어도 이동 계산을 유지한다.

이 이동 계약은 [02 전투](02-Combat.md)의 수평 제어권,
[05 능력·게이트](05-AbilitiesAndGates.md)의 해금 상태,
[09 카메라](09-CameraBounds.md)의 추적 대상과
[16 능력 시험 보스](16-AbilityTrialBoss.md)의 회피 조건으로 재사용된다.

## 10. 한계와 다음 실험

- 코요테·입력 버퍼·공중 자원은 타이머가 Motor에 묶여 있어 프레임 경계를 순수
  테스트하기 어렵다. 다음에는 입력 스냅샷과 이동 상태 계산을 한 단계 더
  분리해 현재 동작을 고정한다.
- 이동 발판과 외부 넉백을 검증하지 않았다. 이를 구현하기 전에
  CharacterController의 플랫폼 속도 합성과 Rigidbody 전환 비용을 최소 실험으로
  비교한다.
- `SideScrollerMotor.Update`가 점프·대시·벽·공격 보정을 모두 조정한다. 새 이동
  상태를 추가할 때 수정 지점이 네 곳 이상으로 늘어나면 상태 모듈 분리를 시작한다.
- 게임패드 실기에서 데드존, 버튼 홀드와 대시 후 달리기 전환을 조정해야 한다.
- 카메라 FOV·화면비가 점프 높이와 이동 속도 체감에 주는 영향은 `09`, `12`
  연구에서 별도로 비교한다.
