# 수직 슬라이스 성능 기준선

## 목표

최적화를 감으로 시작하지 않고 같은 `Main` 씬을 같은 시간 동안 측정해 변경
전후를 비교할 수 있는 기준선을 만든다. 평균만으로 순간 끊김을 숨기지 않도록
프레임 시간과 GC 할당은 95백분위(`p95`)를 함께 기록한다.

## 측정 예산

| 항목 | 프로토타입 예산 | 판정 기준 |
|---|---:|---|
| 프레임 시간 | `16.67 ms` | `p95`가 60 FPS 프레임 예산 이하 |
| GC 할당 | `1,024 B/frame` | 메인 스레드 `p95`가 예산 이하 |
| 드로우 콜 | `150` | 측정 구간 최댓값이 예산 이하 |

지원되지 않는 Recorder는 `0`을 좋은 결과로 오해하지 않고 `unsupported`로
표시해 해당 항목을 판정에서 제외한다. 제외한 항목은 Development Build에서
반드시 다시 측정한다.

## 구현 방식

```text
ProfilerRecorder ── GC.Alloc / Draw Calls Count
Time.unscaledDeltaTime ─────── Frame interval
Profiler memory API ────────── Allocated memory peak
                 │
                 ▼
       최근 600프레임 순환 버퍼
                 │  측정 종료 뒤에만 복사·정렬
                 ▼
 average / p95 / maximum ── Console 기준선
```

- `RuntimePerformanceProbe`는 `1.5초` 워밍업 뒤 `5초` 동안 자동 수집한다.
- 고정 배열에 값 형식만 기록하고, 버퍼가 차면 가장 오래된 샘플부터
  덮어쓴다. 높은 프레임에서도 5초 측정을 조기에 끝내지 않는다.
- `GC.Alloc`은 현재 메인 스레드만 수집해 에셋 임포트 같은 백그라운드 작업의
  영향을 줄인다.
- 통계 배열 복사, 정렬과 로그 문자열 생성은 측정이 끝난 뒤에만 수행한다.
- 포커스가 Terminal로 이동해도 측정 시간이 멈추지 않도록 수집 중에만
  `Application.runInBackground`를 켜고 원래 값을 복원한다.
- Editor 또는 Development Build에서 `F8`을 누르면 전투나 보스 패턴 도중
  같은 조건으로 다시 측정할 수 있다.

## 2026-07-28 Editor 기준선

| 환경 | 값 |
|---|---|
| 장치 | MacBook Pro, Apple M4 Pro 12코어, 24 GB |
| OS / Unity | macOS 26.5.2 / Unity `6000.5.5f1` |
| 구간 | `Main`, 1.5초 워밍업 + 5초 수집 |
| 보존 샘플 | 관측 2,268프레임 중 최근 600프레임 |
| 프레임 시간 | 평균 `1.97 ms`, p95 `2.20 ms`, 최대 `2.78 ms` |
| 메인 스레드 GC | 평균 `4,441 B`, p95 `5,124 B` |
| 드로우 콜 | 현재 Editor 세션에서 `unsupported` |
| 할당 메모리 최고점 | `410.9 MB` |
| 종합 | `CHECK` |

프레임 시간은 60 FPS 예산을 넉넉히 통과했다. GC는 에디터의 플레이 루프와
진단 코드가 함께 실행되는 환경에서 목표를 넘었고 드로우 콜도 이 세션에서
제공되지 않았으므로, 두 항목은 PC Development Build의 실제 Player를
Profiler에 연결해 확정해야 한다. 이 결과를 Release 성능이라고 표현하지
않는다.

## 코드 감사와 최적화 판단

상시 실행되는 이동, 카메라, 애니메이터, 피드백과 안내 `Update` 경로에서는
컬렉션 생성이나 문자열 조합을 찾지 못했다. 현재 가장 명확한 부하 후보는
원거리 적과 보스가 발사 때마다 수행하는 다음 작업이다.

- `GameObject.CreatePrimitive`와 여러 컴포넌트 추가
- 발사마다 `MaterialPropertyBlock` 생성
- 탄환 해결 시 `Destroy`

하지만 현재 기본 구간의 프레임 `p95`에는 병목 증거가 없다. 먼저 보스 탄막
도중 `F8` 기준선과 Player Profiler의 `GC.Alloc` 호출 스택을 확보하고,
발사 순간 스파이크가 재현될 때 탄환 Prefab 풀을 도입한다. 측정 없이 풀링부터
추가하면 수명·이벤트 해제 복잡도만 늘 수 있기 때문이다.

## 2026-07-29 Development Player 기준선

macOS Development Build를 1280×720 창 모드로 실행해 `Main`과
`start_hall` 스트리밍 뒤 자동 기준선을 측정했다.

| 항목 | 값 |
|---|---|
| 관측 프레임 | 3,444프레임 중 최근 600프레임 |
| 프레임 시간 | 평균 `0.98 ms`, p95 `3.63 ms`, 최대 `4.22 ms` |
| 메인 스레드 GC | 평균 `0 B`, p95 `0 B` |
| 드로우 콜 | `unsupported` |
| 할당 메모리 최고점 | `86.8 MB` |
| 종합 | `PASS` |

Editor에서 보이던 GC p95 `5,124 B`가 같은 시작 구역의 Player에서는
`0 B`였으므로 해당 값은 게임 로직의 지속 할당보다 Editor 실행 환경의
영향이라는 근거가 생겼다. 드로우 콜은 여전히 지원되지 않아 별도 Profiler
연결 측정 대상으로 유지한다.

## 자동 테스트

- 통계가 입력 배열을 변경하지 않고 평균·nearest-rank p95·최댓값을 계산한다.
- 요청 샘플 수와 음수 값을 안전하게 제한한다.
- 프레임·GC·드로우 콜 예산의 통과와 실패를 판정한다.
- 플랫폼에서 지원하지 않는 Recorder를 실제 0으로 취급하지 않는다.
- `Main` 씬에 1개의 구성 완료된 Probe가 있고 자동 측정 상태인지 확인한다.
- EditMode `157/157`, PlayMode `4/4` 전체 회귀 테스트를 통과했다.

## 다음 측정 절차

1. 전체 플레이 회귀 테스트에서 보스방까지 진행한다.
2. 투사체가 가장 많은 패턴이 시작되면 `F8`을 누른다.
3. Console의 `[Performance Baseline]` 한 줄을 이 문서 표와 비교한다.
4. macOS Development Build의 시작 구역 기준선과 비교한다.
5. Unity Profiler를 연결해 드로우 콜과 보스 패턴 호출 스택을 확인한다.
6. 예산을 넘는 항목의 Timeline 호출 스택을 근거로 한 기능만 최적화한다.

## 한계

- 현재 값은 Apple Silicon Editor의 단일 짧은 구간이므로 최소 사양 PC의
  대표값이 아니다.
- 프레임 간격은 병목 탐색용 고수준 신호이며 CPU·Render Thread·GPU 시간을
  분리하지 않는다.
- 최근 600프레임만 보존하므로 오래된 일회성 스파이크는 최종 표에서 빠질 수
  있다. 전체 구간 스파이크 원인은 Unity Profiler Timeline으로 확인한다.
