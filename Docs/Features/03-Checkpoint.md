# 03. 체크포인트 — 실패 복구의 기준점은 누가 소유하는가?

> 결론 요약: 월드의 `Checkpoint`는 접촉과 표현만 담당하고,
> `PlayerCheckpointState`가 마지막 ID·부활 좌표와 회복 결과를 소유한다. 현재의
> 작은 Additive 월드에서는 즉시 부활 좌표를 함께 저장하는 방식이 단순하지만,
> 레벨 배치가 자주 바뀌거나 빠른 이동이 추가되면 ID로 현재 위치를 해석하는
> Registry 방식이 더 안전하다.

## 1. 장르에서의 역할

체크포인트는 탐험 실패의 비용을 정한다. 너무 멀면 새 경로를 시험하기 어렵고,
너무 잦으면 공간을 기억하고 지름길을 여는 가치가 약해진다. 기술적으로는 사망,
회복, 저장과 Scene 수명이 만나는 기준점이다.

- 플레이어 경험: 접촉 즉시 안전 지점이 갱신되고 체력이 완전히 회복된다.
- 탐험 연결: 새 구역과 어려운 조우 전후에 귀환 거리의 기준을 제공한다.
- 부활 연결: 체크포인트는 플레이어를 직접 이동시키지 않고 복구 Controller가
  기록된 위치를 읽는다.
- 저장 연결: ID와 좌표는 영구 데이터로 복원되지만 불러오기 자체는 회복·접촉
  이벤트를 다시 발생시키지 않는다.

## 2. 연구 질문과 성공 조건

### 연구 질문

체크포인트의 Trigger·시각 표현·회복·부활 위치·영구 저장을 한 오브젝트에
모으지 않으면서, 실제 접촉과 저장 복원을 어떻게 서로 다른 부작용으로 처리할
것인가?

### 성공 조건

- 유효한 접촉은 ID와 유한한 좌표를 원자적으로 기록하고 완전 회복한다.
- 빈 ID, NaN과 Infinity 좌표는 체력과 기존 상태를 바꾸지 않는다.
- 저장 복원은 상태만 적용하고 회복·활성 이벤트를 재생하지 않는다.
- 새 게임 초기화는 ID, 좌표와 보유 여부를 모두 제거한다.
- 월드 Trigger는 체력·사망·Teleport 순서를 직접 소유하지 않는다.

## 3. 현재 구현 분석

| 코드 | 책임 | 장르 경험으로 이어지는 결과 |
|---|---|---|
| `Checkpoint.cs` | Trigger 접촉, ID·Offset 전달, 활성 색상 | 월드 오브젝트를 밟아 안전 지점 활성화 |
| `PlayerCheckpointState.cs` | 마지막 ID·좌표 검증과 보유, 접촉 시 회복 | Scene 오브젝트가 사라져도 부활 기준 유지 |
| `Health.cs` | 현재·최대 체력과 완전 회복 이벤트 | 체크포인트 정책이 내부 체력 값을 직접 쓰지 않음 |
| `PlayerRespawnController.cs` | 사망 뒤 기록 위치로 이동하는 순서 | 체크포인트와 사망 연출·입력 잠금 분리 |
| `GameProgressSaveData.cs` | 체크포인트 상태의 Snapshot·Restore | 앱 종료 뒤 같은 진행 기준 복원 |

### 실행 흐름

```text
플레이 중 접촉
Collider → Checkpoint.Activate
  → PlayerCheckpointState가 ID·좌표 검증
  → 상태 기록 → Health 완전 회복
  → CheckpointActivated 이벤트
  → 월드 시각 활성화

저장 불러오기
Save DTO → RestoreCheckpoint
  → ID·좌표 검증 → 상태만 기록
  → 회복·접촉 이벤트 없음
```

접촉과 복원 API를 나눈 이유는 결과의 의미가 다르기 때문이다. 불러오기 때
`ActivateCheckpoint`를 재사용하면 저장 당시 체력 정책과 무관하게 완전 회복되고,
자동 저장·튜토리얼 구독자도 새 접촉으로 오인할 수 있다.

### 상태 소유권

| 상태 | 소유자 | 소유하지 않는 것 |
|---|---|---|
| 현재·최대 체력 | `Health` | 체크포인트 위치와 ID |
| 마지막 ID·부활 좌표 | `PlayerCheckpointState` | Trigger와 월드 표현 |
| 접촉·활성 색상 | `Checkpoint` | 플레이어 이동과 사망 순서 |
| 사망 뒤 복구 순서 | `PlayerRespawnController` | 체크포인트 선택 정책 |

`MaterialPropertyBlock`을 사용해 활성 색상을 바꾸므로 공유 Material을 복제하거나
다른 체크포인트의 색을 함께 바꾸지 않는다.

## 4. 구현 후보 비교

### 상태 위치

| 후보 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 플레이어 전용 상태 (현재) | 부활·저장 시스템이 Scene 오브젝트 없이 읽기 쉬움 | 로컬 협동·여러 캐릭터면 소유 관계 재설계 필요 | 한 명의 플레이어와 연속 진행 |
| Checkpoint 오브젝트가 활성 상태 소유 | 구현이 직관적이고 작은 Scene에서 빠름 | Scene Unload 뒤 참조 소실, 마지막 지점 검색 필요 | 저장 없는 단일 Scene 게임 |
| 전역 Progress Manager | 어느 Scene에서도 접근이 쉬움 | 의존성이 숨고 테스트 격리가 어려움 | 이미 중앙 세션 상태와 DI 경계가 있는 프로젝트 |
| Save/World State만 소유 | 영구 상태의 단일 원본 | 매 접촉과 부활이 저장 모델에 직접 결합 | 서버 권위 또는 항상 영속화하는 구조 |

### 부활 위치 표현

| 후보 | 장점 | 단점 | 선택 조건 |
|---|---|---|---|
| ID + 좌표 Snapshot (현재) | Registry와 Scene 로드 없이 즉시 부활 가능 | 레벨 수정 뒤 오래된 좌표가 벽·공중에 남을 수 있음 | 작은 고정 Graybox와 단일 버전 프로토타입 |
| ID만 저장 + Registry 해석 | 현재 레벨 배치를 항상 사용 | 대상 Scene 로드와 ID Registry가 먼저 필요 | 레벨이 자주 수정되고 빠른 이동·다중 Scene이 있는 게임 |
| Scene + Spawn Index | 구현이 단순함 | Scene 이름·Hierarchy 변경과 저장이 결합 | Scene 구성이 거의 변하지 않는 짧은 게임 |

### 회복 정책 위치

현재는 `PlayerCheckpointState.ActivateCheckpoint`가 항상 완전 회복한다. 하나의
체크포인트 종류에서는 원자적이고 단순하지만, 휴식 비용·부분 회복·적 재생성 같은
정책이 늘면 Checkpoint Service 또는 Rest Policy로 분리하는 편이 낫다.

## 5. 선택과 전환 기준

### 현재 프로젝트에서의 선택

- 선택: 월드 표현과 플레이어 상태 분리, ID와 좌표를 함께 Snapshot
- 우선 기준: Additive Scene이 Unload되어도 부활 정보 유지, 단순한 저장 왕복
- 감수한 단점: 좌표가 레벨 버전 변화에 취약하고 회복 정책이 상태 객체에 결합됨
- 보완: ID·유한 좌표 검증, 접촉과 저장 복원 API 분리, 부활 실행은 별도
  Controller가 담당

### 다른 방식이 더 나은 경우

- 체크포인트 위치가 Release 사이에서 바뀜: ID Registry로 현재 Transform 해석
- 빠른 이동과 체크포인트 선택 UI 추가: 월드 정의에 ID·Scene·표시 이름 등록
- 부분 회복·자원 충전·적 재생성 정책 추가: Rest Service로 부작용 이동
- 여러 플레이어 또는 저장 슬롯 동시 실행: Player Component보다 Session State가
  체크포인트 소유

전환 신호는 중복 ID가 실제로 발생하거나, 저장 좌표가 지형 안에 복원되거나,
체크포인트 종류별 `if`가 `PlayerCheckpointState`에 추가되는 시점이다.

## 6. 핵심 판단 읽기

```text
ID가 비어 있음 또는 좌표가 유한하지 않음
  → 아무 상태도 바꾸지 않고 실패

유효한 접촉
  → HasCheckpoint = true
  → ID Trim + 좌표 기록
  → 완전 회복
  → 활성 이벤트
```

검증을 모든 대입보다 먼저 수행하므로 실패가 부분 상태를 만들지 않는다. 저장
복원도 같은 입력 검증을 사용하지만 회복과 이벤트는 생략한다. 이 차이는 저장
데이터 적용을 과거 접촉의 재실행이 아니라 상태 Snapshot 복원으로 정의한다.

## 9. 결론

- 체크포인트는 월드 오브젝트보다 오래 사는 진행 상태다.
- 실제 접촉과 저장 복원은 같은 값을 만들더라도 부작용이 다르므로 API를 나눠야
  한다.
- ID와 좌표를 함께 저장하는 현재 방식은 단순하지만, 콘텐츠 수정 안정성까지
  요구되면 ID Registry가 필요하다.
- 회복, 저장, 부활을 한 Trigger에 넣지 않아 다음 단계가 각자 같은 상태를
  재사용할 수 있다.

이 계약은 [04 사망·재시작](04-Respawn.md)의 목적지,
[17 진행 저장](17-ProgressSave.md)의 영구 Snapshot과
[18 진행 HUD](18-ProgressHud.md)의 상태 전달로 이어진다.

## 10. 한계와 다음 실험

- 중복 체크포인트 ID를 빌드 전에 검사하는 Registry가 없다.
- 좌표 Snapshot은 레벨 수정 뒤 안전하지 않다. ID 해석 방식과 저장 마이그레이션
  비용을 `17` 연구에서 비교한다.
- 여러 체크포인트의 활성 색상을 동기화하지 않아 마지막 지점만 강조하는 표현이
  완전하지 않다.
- 체크포인트 접촉 시 적 재생성·자원 충전 정책이 없다. 정책이 둘 이상 생길 때
  Rest Service 분리를 검토한다.
- 촬영 자료와 부활 위치 Collider 안전성 PlayMode 테스트가 필요하다.
