# 아키텍처와 비교 실험 규칙

이 문서는 현재 구현의 의존 방향과 앞으로 구조를 비교·변경할 때 지켜야 할
경계를 정의한다. 규칙은 절대적인 정답이 아니며, 예외가 더 적합하면 기능
문서에 이유와 영향 범위를 기록한다.

## 1. 기본 의존 방향

```text
Input
  ↓
Feature Controller ──→ Physics / Scene / Animation
  ↓                              ↓
Pure Rule + Runtime State ──→ Confirmed Event
                                   ↓
                         Feedback / UI / Save
```

- 입력 액션은 게임 규칙을 직접 완료하지 않고 Controller에 의도를 전달한다.
- Unity 생명주기, 물리 질의와 실제 이동은 `MonoBehaviour`가 담당한다.
- 수치 계산과 상태 판단은 가능한 한 `*Math`, 규칙 객체 또는 직렬화 가능한
  데이터로 분리한다.
- VFX·SFX·UI는 시도 이벤트가 아니라 게임플레이에서 확정된 결과를 구독한다.
- 저장 계층은 Transform이나 Scene 오브젝트 참조가 아니라 영구 ID와 값만
  직렬화한다.

이 구조의 목적은 모든 코드를 순수 함수로 만드는 것이 아니다. Unity 실행과
장르 규칙의 경계를 드러내 어떤 부분을 EditMode에서 검증하고 어떤 부분을
PlayMode와 실제 플레이로 확인할지 명확하게 하는 것이다.

## 2. 상태 소유 원칙

| 상태 | 기본 소유자 | 이유 |
|---|---|---|
| 현재 입력·짧은 타이머 | 기능 Controller | 프레임과 Unity 실행 순서에 밀접함 |
| 체력·능력·현재 구역 | 전용 Runtime State | UI·저장·월드가 같은 상태를 구독함 |
| 구역·능력·패턴 정의 | ScriptableObject 또는 불변 설정 | 콘텐츠 정의와 플레이 세션을 분리함 |
| 영구 진행 | 버전형 Save DTO | Scene과 앱 수명보다 오래 유지됨 |
| VFX·SFX 표시 상태 | Feedback 계층 | 판정과 표현 변경을 독립시킴 |

여러 객체가 같은 값을 복사해 가지면 원본 소유자와 동기화 시점을 기능 문서에
명시한다.

## 3. 메트로배니아 시스템 계약

### 이동 ↔ 능력

이동 Controller는 구체적인 Pickup을 알지 않고 `PlayerAbilityState`의 보유
계약만 확인한다. 능력 획득 방식이 바뀌어도 이동 규칙은 ID의 의미만 유지한다.

### 능력 ↔ 월드

게이트와 보상은 플레이어 클래스를 직접 수정하지 않고 능력·수집·지름길 ID를
통해 조건을 표현한다. 레벨 오브젝트 교체가 저장 데이터의 의미를 바꾸지 않아야
한다.

### 전투 ↔ 생존

공격자와 적 AI는 구체적인 플레이어 구현보다 `Health`, `DamageRules`와 무적
계약을 사용한다. 피격 확정 뒤에만 피드백과 사망 복구가 이어진다.

### 구역 ↔ 카메라·지도·스트리밍

현재 구역은 하나의 `PlayerWorldState`가 소유한다. Trigger, 카메라, 지도와
스트리밍은 각자 위치를 다시 추측하지 않고 이 상태와 영구 구역 정의를 사용한다.

### 런타임 ↔ 저장

저장 Controller는 각 상태 소유자에게서 스냅샷을 모으고 DTO로 변환한다. 불러온
데이터는 검증과 마이그레이션을 거친 뒤 상태 객체에 적용하며, 표현 계층은 복원
이벤트에 반응한다.

## 4. 실험 환경 경계

- `Main`: 전체 장르 루프, 시스템 간 결합, 저장·부활·백트래킹 회귀 검증
- `CaptureStudio`: 넓은 간격에서 이동·공격·적 패턴을 반복 촬영하는 통제 환경
- EditMode: 순수 계산, 상태 전환, ID와 직렬화 계약
- PlayMode: Collider, 투사체, Scene 로드와 Unity 생명주기
- Development Build: Editor 오버헤드가 없는 성능과 실제 실행 검증

촬영 단축키나 실험용 배치는 `CaptureStudio` 계층에만 두고 Runtime 계약을
우회하지 않는다. 실험에서만 필요한 대안 구현은 제품 코드와 Assembly를 분리한다.

## 5. 리팩터링 결정 순서

```text
실패 사례 재현
  → 현재 계약을 테스트로 고정
  → 책임과 상태 소유자 추적
  → 대안의 이득·비용 비교
  → 최소 변경 또는 실험 구현
  → 통합 플레이 회귀
  → 문서에 적용 조건과 전환 신호 기록
```

다음 상황은 구조 변경을 검토할 신호다.

- 새 능력 하나가 이동·게이트·저장 코드의 조건문을 모두 수정하게 한다.
- Scene 이름이나 Hierarchy 변경만으로 저장 데이터가 무효가 된다.
- 같은 상태 전환 규칙이 둘 이상의 Controller에 중복된다.
- 플레이 버그를 Scene 전체 실행 없이는 재현할 수 없다.
- 프레임당 검색이나 할당이 실제 성능 예산을 반복해서 초과한다.
- 디자이너 수치 조정마다 컴파일과 코드 변경이 필요하다.

신호가 없으면 미래 확장을 예상한 추상화보다 단순하고 관찰 가능한 구조를
유지한다.

## 6. C# 작성 기준

- 파일 상단에 `GOLDEN STANDARD` 블록으로 목적, 책임, 비책임과 주요 계약을
  한글로 작성한다.
- 함수 주석은 “무엇을 반환한다”보다 그 경계를 함수로 분리한 이유를 설명한다.
- 조건문 주석은 플레이 규칙이나 예외의 의도를 설명한다.
- 반복문 주석은 순회 대상, 조기 종료 조건과 비용을 설명한다.
- 이름으로 충분히 드러나는 대입이나 단순 반환을 그대로 번역하는 주석은 피한다.
- 공개 SerializeField에는 조정 범위와 플레이 영향이 Inspector에서 이해되도록
  설명을 둔다.
- 순수 계산은 경계값 테스트를 우선하고, Unity API가 필요한 계약만 PlayMode로
  올린다.

기존 코드의 주석은 기능 문서 개편 중 해당 파일을 실제로 분석할 때 함께
감사한다. 문맥을 확인하지 않은 기계적인 주석 추가는 하지 않는다.
