# game_skill 프로젝트 계획서

## 1. 프로젝트 정의

`game_skill`은 Unity 6.5로 만든 2.5D 메트로배니아 Reference
Implementation과 그 구현을 분석하는 연구형 포트폴리오다.

플레이 가능한 프로토타입은 이미 핵심 루프를 갖추었다. 앞으로의 중심 작업은
콘텐츠를 계속 늘리는 것이 아니라, 현재 코드를 장르 질문 단위로 분석하고 다른
구현 방식과 비교해 상황별 선택 기준을 남기는 것이다.

### 최종 목표

- 이동 능력 획득, 게이트, 백트래킹, 지름길, 저장, 보스까지 이어지는 장르
  루프를 실제 플레이로 검증한다.
- 핵심 시스템마다 현재 구현과 유효한 대안을 공통 기준으로 비교한다.
- 선택 이유뿐 아니라 한계, 포기한 점, 구조를 교체할 시점을 설명한다.
- 코드, 자동 테스트, 플레이 GIF가 같은 결론을 증명하도록 연결한다.

게임 경험의 기준은 [게임 디자인 문서](GAME_DESIGN.md), 연구 방법은
[메트로배니아 개발 연구 계획](METROIDVANIA_STUDY.md)을 따른다.

## 2. 현재 자산의 역할

| 자산 | 새 방향에서의 역할 |
|---|---|
| `Assets/Scenes/Main.unity` | 모든 시스템이 연결된 장르 루프와 회귀 테스트 환경 |
| `Assets/Scenes/CaptureStudio.unity` | 이동·전투·적 기능을 독립 비교하는 촬영·실험 환경 |
| `Assets/Scripts/Runtime` | 현재 선택을 보여주는 Reference Implementation |
| `Assets/Tests` | 리팩터링 전후에 유지해야 할 동작 계약 |
| `Docs/Features` | 코드 선택과 적용 조건을 설명하는 연구 기록 |
| `Media` | 플레이어가 체감하는 차이를 보여주는 시각 증거 |

기존 프로토타입과 번호 체계는 삭제하거나 처음부터 다시 만들지 않는다. 먼저
동작을 보존한 뒤, 비교 결과가 실제 한계를 드러낸 시스템만 선택적으로
리팩터링한다.

## 3. 기술 기준

- Unity: `6000.5.5f1`
- Editor: macOS ARM64
- Render Pipeline: URP
- Input: Unity Input System
- 이동 평면: X/Y, Z축은 2.5D 시각 깊이에 사용
- 데이터: ScriptableObject와 안정적인 문자열 ID
- 테스트: Unity Test Framework의 EditMode·PlayMode
- 바이너리 에셋: Git LFS

Unity 버전과 핵심 패키지는 비교 변수에 포함되지 않는 한 고정한다. 버전 변경은
기능 연구와 분리된 커밋으로 수행한다.

## 4. 연구 원칙

1. 기능 이름보다 장르에서 만들려는 경험을 먼저 정의한다.
2. 후보 구현은 플레이 감각, 레벨 디자인, 결합도, 테스트, 확장, 비용으로
   비교한다.
3. 현재 구현은 정답이 아니라 현재 제약에서 선택한 기준점으로 다룬다.
4. 자동 테스트가 보장하는 계약과 실제 플레이로 판단한 손맛을 구분한다.
5. 대안의 차이가 의미 있을 때만 최소 실험 코드를 작성한다.
6. 리팩터링 전에는 기존 동작을 테스트와 영상으로 고정한다.
7. 능력은 이동·전투·월드 중 최소 두 맥락에서 의미가 있는지 검증한다.
8. 영구 진행은 Scene 오브젝트 직접 참조보다 안정적인 ID로 표현한다.
9. 기능 문서 하나가 완료될 때 관련 변경만 커밋하고 원격 저장소에 푸시한다.

## 7. 변경 판단 규칙

| 관찰 | 우선 행동 | 바로 리팩터링하지 않는 이유 |
|---|---|---|
| 문서만 설명이 부족함 | 실제 코드 분석과 비교표 보강 | 동작 위험 없이 지식 공백부터 확인 가능 |
| 경계값 테스트가 없음 | 현재 동작을 테스트로 고정 | 구조 변경 효과와 기존 회귀를 구분하기 위함 |
| 동일 책임이 여러 컴포넌트에 중복됨 | 호출 흐름과 상태 소유자 측정 | 겉보기 중복이 Unity 생명주기 경계일 수 있음 |
| 기능 추가마다 같은 파일을 수정함 | 대안 최소 실험 후 확장 구조 비교 | 추상화가 현재 규모보다 비쌀 수 있음 |
| 플레이 실패가 반복됨 | 영상·로그·수치로 실패 재현 | 감각 문제와 구조 문제를 분리하기 위함 |
| 성능 예산을 초과함 | Profiler로 호출 원인 확인 | 근거 없는 풀링·캐싱은 복잡도만 늘릴 수 있음 |

## 8. 과거 구현 마일스톤

기존 M0~M7은 프로토타입이 어떻게 성장했는지 보여주는 이력으로 보존한다.

| 마일스톤 | 결과 | 상태 |
|---|---|---|
| M0 기반 | Unity·URP·Input System·Git LFS·CC0 에셋 | 완료 |
| M1 이동·카메라 | 가속, 점프 보정, 대시, 공중 능력, 벽 이동, 2.5D 카메라 | 완료 |
| M2 전투·생존 | 콤보, 자동 조준, 체력, 체크포인트, 부활 | 완료 |
| M3 능력·게이트 | ScriptableObject 능력, ID 보유 상태, 세 이동 게이트 | 완료 |
| M4 연결 월드 | 구역, 지름길, Additive 스트리밍, 지도, 백트래킹 보상 | 완료 |
| M5 적·보스 | 근거리·원거리·돌진 적과 능력 시험 보스 | 완료 |
| M6 저장·UI | 버전형 JSON, HUD, Pause와 음량 | 완료 |
| M7 검증·빌드 | 피드백, 튜토리얼, 성능 기준선, macOS 빌드 | 완료 |

이 표는 완료 기능을 자랑하기 위한 체크리스트가 아니라, 앞으로 분석할 실제
사례의 범위를 나타낸다.

## 9. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 비교가 장단점 나열로 끝남 | 적용 조건과 구조 전환 신호를 필수 항목으로 둔다. |
| 모든 대안을 실제 구현해 범위가 폭증함 | 플레이·확장 판단에 차이가 있을 때만 최소 실험한다. |
| 문서와 코드가 다시 어긋남 | 문서마다 실제 클래스·테스트·미디어 링크를 검증한다. |
| 기존 플레이 동작이 리팩터링으로 깨짐 | 변경 전 계약 테스트와 통합 회귀 동선을 고정한다. |
| 참고작 복제로 보임 | 장르 원칙만 관찰하고 코드·맵·시각 자산은 독립 제작한다. |
| 연구 방향 때문에 공개가 계속 미뤄짐 | 연구 축 하나가 끝날 때 독립적으로 읽을 수 있는 상태로 푸시한다. |
