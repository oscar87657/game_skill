# 포트폴리오 운영 계획

이 저장소는 메트로배니아 기능을 많이 구현했다는 사실보다, 장르 경험을 만드는
코드 선택을 분석하고 상황별 판단 기준을 설명하는 기술 포트폴리오다.

## 독자와 전달 목표

- 주 독자: 게임플레이 프로그래머와 기술 면접 검토자
- 보조 독자: 메트로배니아 시스템을 공부하는 개발자와 미래의 나
- 첫 화면에서는 연구 질문과 결론을 빠르게 읽을 수 있어야 한다.
- 세부 문서에서는 코드·테스트·플레이 증거로 결론을 다시 확인할 수 있어야 한다.

## 프로토타입의 역할

| 환경 | 역할 | 여기서 검증하는 것 |
|---|---|---|
| `Main` | 통합 Reference Implementation | 능력 해금, 구역 이동, 백트래킹, 저장, 보스까지 이어지는 장르 루프 |
| `CaptureStudio` | 통제된 기능 실험실 | 이동·공격·적 패턴처럼 짧게 반복해야 하는 단일 변수 |
| EditMode 테스트 | 규칙 실험 | 수치 계산, 경계값, 상태 전환, 직렬화 계약 |
| PlayMode 테스트 | Unity 통합 실험 | 물리 질의, Scene 생명주기, 투사체와 스트리밍 |

프로토타입은 완성품을 흉내 내는 전시물이 아니라, 비교 결과를 실제 플레이로
확인할 수 있는 공통 시험대다.

## 문서 읽는 두 경로

### 장르 연구 경로

[기능 구현 인덱스](FEATURE_INDEX.md)의 연구 축을 따라 읽는다.

```text
이동 감각
  → 전투와 이동 결합
  → 능력 진행과 게이트
  → 월드 연결과 백트래킹
  → 적을 통한 능력 시험
  → 영구 진행과 제작 검증
```

서로 떨어진 시점에 구현한 기능도 같은 장르 질문에 답한다면 함께 비교한다.

### 구현 발전 경로

기존 `01 → 23` 번호를 따라 읽는다. 이 경로는 앞 단계의 계약이 다음 기능에서
어떻게 재사용됐는지 보여주며 Git 이력과 촬영 파일 번호도 그대로 연결한다.

## 한 문서의 서술 순서

```text
장르에서의 역할
  → 관찰한 문제와 성공 조건
  → 현재 코드 책임과 실행 흐름
  → 후보 방식 비교
  → 현재 선택과 전환 기준
  → 테스트·플레이 증거
  → 한계와 다음 실험
```

- 구현 설명 전에 플레이어 경험과 레벨 디자인 영향을 먼저 적는다.
- 대안은 장점과 단점만 나열하지 않고, 어느 규모와 조건에서 선택할지 적는다.
- 현재 방식도 무조건 옹호하지 않는다. 실제 한계와 교체 신호를 기록한다.
- 코드 조각은 문법 소개가 아니라 중요한 판단 경계 하나를 설명한다.
- GIF는 조작 키보다 코드 규칙이 만든 차이를 보여준다.

## 기능 단위 완료 기준

- [ ] 장르에서 이 기능이 담당하는 경험이 정의되어 있다.
- [ ] 현재 구현의 책임과 의존 방향이 실제 코드와 일치한다.
- [ ] 비교 후보가 두 개 이상이며 선택 조건이 구체적이다.
- [ ] 현재 선택과 포기한 점, 다른 구조로 전환할 신호가 기록되어 있다.
- [ ] 정상·경계·실패 중 중요한 계약이 테스트되었다.
- [ ] `Main` 또는 `CaptureStudio`에서 플레이 결과를 재현할 수 있다.
- [ ] 결론을 뒷받침하는 GIF·스크린샷·수치 중 하나 이상이 있다.
- [ ] 관련 문서와 인덱스 링크가 갱신되어 있다.

## 연구 진행 순서

### R1. 이동 범위와 조작 감각

`01`, `09`, `12`를 중심으로 직접 제어와 물리 기반 이동, 점프 보정, 대시
곡선, 벽 이동, 추적 카메라의 선택 기준을 분석한다.

### R2. 전투가 이동을 방해하지 않는 구조

`02`, `13`, `14`, `15`, `20`을 중심으로 공격 상태, 이동 권한, 무적 계약,
예고와 피드백의 책임 경계를 비교한다.

### R3. 능력이 월드를 바꾸는 방법

`05`, `11`, `16`을 중심으로 능력 표현 방식, 게이트 조건, 재방문 보상과
전투 시험이 하나의 능력을 어떻게 다른 맥락에서 재사용하는지 분석한다.

### R4. 연결된 월드와 위치 이해

`06`~`10`, `12`를 중심으로 구역 식별, 지름길, 스트리밍, 지도와 카메라가
백트래킹 중 길 찾기에 주는 영향을 비교한다.

### R5. 실패와 영구 진행 복구

`03`, `04`, `17`~`19`를 중심으로 체크포인트, 부활, 저장 DTO, HUD와 Pause가
런타임 상태와 영구 상태를 어떻게 나누는지 분석한다.

### R6. 검증 가능한 제작 과정

`21`~`23`과 전체 테스트를 중심으로 튜토리얼, 성능 기준, 재현 가능한 빌드가
플레이 가능한 연구 결과를 어떻게 유지하는지 정리한다.

## Git 운영

- 기능 문서 하나를 새 기준으로 완성할 때 해당 문서와 관련 증거만 커밋한다.
- 여러 중앙 문서가 하나의 탐색 구조를 만들 때는 하나의 문서 구조 변경으로
  묶을 수 있다.
- 코드 실험은 문서 변경과 분리하고, 동작 계약 테스트를 먼저 추가한다.
- 기존 기능 번호와 미디어 파일명은 링크 안정성을 위해 변경하지 않는다.
- Unity 복구 파일과 촬영 중 변경된 Material은 관련 작업이 아니면 커밋하지 않는다.

## 공개 단위

첫 공개 기준은 콘텐츠 분량이 아니라 다음 질문에 답할 수 있는가이다.

1. 메트로배니아 핵심 루프가 실제로 처음부터 끝까지 동작하는가?
2. 각 핵심 시스템에 최소 하나의 구현 비교와 선택 기준이 있는가?
3. 코드, 테스트, GIF가 같은 결론을 가리키는가?
4. 요구사항이 커질 때 구조를 바꿔야 할 신호가 기록되어 있는가?

상세 연구 방법은 [메트로배니아 개발 연구 계획](METROIDVANIA_STUDY.md)을
기준으로 한다.
