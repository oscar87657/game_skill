# 메트로배니아 개발 연구 계획

이 프로젝트의 최종 산출물은 단순한 기능 모음이 아니다. 플레이 가능한 하나의
프로토타입을 실험장으로 사용해, 메트로배니아를 구성하는 시스템이 서로 어떤
영향을 주는지 분석하고 구현 선택의 기준을 남기는 것이 목표다.

## 1. 연구 목표

다음 세 질문에 코드와 플레이 결과로 답한다.

1. 메트로배니아의 탐험·능력 해금·백트래킹 경험은 어떤 시스템 계약으로
   만들어지는가?
2. 같은 기능을 구현하는 여러 방식은 프로젝트 규모와 콘텐츠 요구에 따라 어떤
   장단점을 가지는가?
3. 현재 구현은 왜 이 프로토타입에 적합하며, 요구사항이 바뀌면 어느 지점부터
   다른 구조로 전환해야 하는가?

`Main`은 모든 시스템이 연결된 통합 검증 환경이고, `CaptureStudio`는 하나의
변수만 바꾸어 비교하는 통제된 실험 환경이다. 현재 코드는 정답이 아니라 비교의
기준점인 **Reference Implementation**으로 취급한다.

## 2. 연구 대상

| 연구 축 | 장르 질문 | 현재 코드로 검증할 내용 |
|---|---|---|
| 플레이어 이동과 감각 | 입력이 즉각적이면서도 능력 획득 전후의 이동 범위를 어떻게 구분하는가? | 가속, 점프 보정, 대시 곡선, 공중 자원, 벽 이동 |
| 전투와 이동의 결합 | 공격이 탐험 조작을 방해하지 않으면서 능력 사용을 유도하려면 무엇을 분리해야 하는가? | 콤보, 공중 제어, 무적, 대상 선택, 피격 계약 |
| 능력 진행과 게이팅 | 능력을 단순 열쇠가 아니라 이동·전투·월드 해석의 변화로 만드는 방법은 무엇인가? | ID 기반 능력 상태, 획득, 게이트, 보스 패턴 |
| 월드 구조와 백트래킹 | 재방문이 반복 이동이 아니라 새로운 판단이 되려면 어떤 상태와 연결이 필요한가? | 구역 ID, 지름길, 스트리밍, 지도, 영구 보상 |
| 카메라와 공간 전달 | 2.5D 공간의 깊이와 진행 방향을 보여주면서 플레이어를 놓치지 않으려면 어떻게 제한하는가? | Perspective, 구역 경계, 추적과 고정 구도 |
| 적과 조우 설계 | 적 패턴이 획득 능력의 사용법을 가르치고 시험하게 하려면 어떻게 구성하는가? | 판단/실행 분리, 예고, 투사체, 돌진, 보스 |
| 영구 진행과 복구 | Scene이 바뀌거나 게임을 종료해도 장르 진행을 안전하게 복원하려면 무엇을 저장해야 하는가? | 체크포인트, 부활, 버전형 저장, 월드 상태 |
| 검증과 제작 운영 | 손맛과 월드 진행처럼 수치화하기 어려운 요소를 어떻게 반복 검증하는가? | 순수 계산 테스트, PlayMode, 촬영 씬, 성능·빌드 자동화 |

## 3. 공통 비교 기준

각 구현 후보를 같은 기준으로 평가한다. 모든 항목에서 우수한 방식은 없으며,
현재 요구사항에서 중요한 기준의 우선순위를 먼저 밝힌다.

| 기준 | 확인 질문 |
|---|---|
| 플레이 감각 | 입력 지연, 관성, 취소 가능 시간이 의도한 리듬을 만드는가? |
| 레벨 디자인 영향 | 거리·높이·게이트 배치 규칙을 예측 가능하게 만들 수 있는가? |
| 장르 확장성 | 능력, 구역, 적, 저장 필드가 늘어날 때 변경 범위가 어디까지인가? |
| 결합도 | 이동·전투·월드·UI 중 하나를 바꿀 때 다른 시스템도 함께 수정해야 하는가? |
| 테스트 가능성 | Unity Scene 없이 핵심 규칙을 재현할 수 있는가? 통합 검증은 어디서 하는가? |
| 디자이너 반복 속도 | 코드 수정 없이 수치와 콘텐츠 조합을 바꿀 수 있는가? |
| 디버깅 가능성 | 현재 상태와 전환 이유를 관찰하고 실패를 재현할 수 있는가? |
| 런타임 비용 | 프레임당 탐색, 할당, 물리 질의와 Scene 유지 비용이 규모에 맞는가? |
| 저장 호환성 | 오브젝트 참조가 바뀌어도 영구 진행을 복원할 수 있는가? |
| 플레이어 전달력 | 예고·UI·카메라·공간 배치가 규칙을 설명 없이 이해시키는가? |

평가는 `좋음/나쁨`으로 끝내지 않는다. 다음과 같이 조건을 붙인다.

- 현재 프로토타입에서 선택할 방식과 이유
- 소규모 단일 Scene에서 더 단순한 대안
- 콘텐츠가 커질 때 전환할 대안과 전환 신호
- 선택으로 포기한 점과 보완 방법

## 4. 한 기능의 연구 절차

```text
장르 경험 정의
  → 현재 코드와 실패 사례 관찰
  → 비교할 구현 후보 2개 이상 선정
  → 공통 기준으로 정적 분석
  → 필요한 경우 작은 대안 구현 또는 계산 실험
  → EditMode·PlayMode·실제 플레이 검증
  → GIF·스크린샷·수치로 결과 기록
  → 적용 조건과 전환 기준 결론
```

비교는 억지로 코드를 두 벌 만드는 작업이 아니다. 차이가 플레이 결과나 유지
비용에 의미가 있을 때만 대안 프로토타입을 만든다. 단순한 대안은 의사 코드와
결정 표로 분석하고, 실제 위험이 있는 경계만 테스트로 검증한다.

## 5. 증거의 수준

| 수준 | 증거 | 용도 |
|---|---|---|
| E1 | 코드 책임 표와 실행 흐름 | 구조가 의도와 일치하는지 설명 |
| E2 | EditMode 테스트 | 계산·상태 전환·저장 계약 검증 |
| E3 | PlayMode 테스트 | Unity 물리·Scene·생명주기 통합 검증 |
| E4 | GIF·스크린샷 | 플레이어가 체감하는 결과 검증 |
| E5 | 프로파일링·회귀 기록 | 성능과 전체 진행의 안정성 검증 |

각 문서는 필요한 수준까지만 사용하되, 결론이 어떤 증거에 근거하는지 표시한다.
손맛은 자동 테스트만으로 증명하지 않고 실제 플레이 기록을 함께 사용한다.

## 6. 코드 변경 원칙

- 이미 잘 동작하는 코드는 문서 비교만을 위해 즉시 교체하지 않는다.
- 비교 결과 현재 구조의 한계가 실제 요구사항을 막을 때 리팩터링한다.
- 리팩터링 전후의 동작 계약을 먼저 테스트로 고정한다.
- Unity 생명주기와 물리 실행은 `MonoBehaviour`, 결정 규칙은 가능한 한 순수
  C#으로 분리한다.
- 영구 진행은 Scene 이름과 직접 참조보다 안정적인 ID를 사용한다.
- 실험용 코드가 제품 코드에 섞이지 않도록 `CaptureStudio` 또는 테스트 계층에
  둔다.
- 새 C# 파일은 상단에 골든 스탠다드와 책임 경계를 적고, 함수와 반복문의 의도를
  설명하는 한글 주석을 사용한다.

## 7. 문서 산출물

각 연구 항목은 다음 묶음으로 완료한다.

1. 장르에서의 역할과 플레이어 경험
2. 현재 구현의 코드 책임과 실행 흐름
3. 후보 구현 비교표
4. 현재 선택의 적용 조건과 전환 기준
5. 테스트와 플레이 증거
6. 실패 사례, 한계, 다음 실험

[기능 구현 인덱스](FEATURE_INDEX.md)는 연구 축에서 관련 문서를 찾는 지도이고,
[기능 문서 템플릿](FEATURE_TEMPLATE.md)은 모든 비교 기록의 공통 형식이다.
[프로젝트 계획서](PROJECT_PLAN.md)는 연구 순서와 완료 기준을 관리한다.

## 8. 범위 밖의 비교

- 상용 게임의 비공개 소스 코드를 추측하거나 복제하지 않는다.
- 참고작의 화면 결과는 디자인 관찰 자료로만 사용한다.
- 다른 구현은 Unity 공식 문서, 공개 기술 자료, 일반적인 설계 패턴과 직접 만든
  최소 실험을 바탕으로 비교한다.
- 세계관·최종 아트·콘텐츠 양은 시스템 판단에 필요한 범위까지만 제작한다.
